# Анализ сетевого трафика с помощью Scapy и эксплуатация XSS на Google Gruyere

---

## 1. Цели работы

1. Изучить и освоить библиотеку **Scapy** для низкоуровневого перехвата сетевых пакетов, фильтрации трафика по протоколам и сохранения/чтения дампов в формате `.pcap`.
2. Реализовать парсер и анализатор HTTP-трафика на базе Scapy, способный восстанавливать TCP-потоки, анализировать структуру запросов/ответов и автоматически декомпрессировать сжатые данные (`Content-Encoding: gzip`).
3. Провести рекон-анализ веб-приложения **Google Gruyere** и найти уязвимости внедрения клиентских сценариев (**Cross-Site Scripting, XSS**).
4. Проэксплуатировать уязвимости XSS, зафиксировать атаку в сетевом трафике и выявить ключевые отличия атакующего трафика от легитимного.

## 3. Окружение и настройка инструментов

### 3.1. Установленное ПО и библиотеки
* **Python**: версия `3.15.2`.
* **Библиотеки Python**:
  - `scapy==2.8.0` — низкоуровневый анализ сетевых пакетов, BPF-фильтрация, сборка и чтение PCAP.
  - `requests==2.34.2` — генерация легитимных и вредоносных HTTP-запросов.

Для захвата «сырых» сетевых пакетов (raw sockets / promiscuous mode) в ОС Windows запуск скриптов осуществляется с правами Администратора (Run as Administrator) либо через пользователя с доступом к драйверу Npcap.

## 4. Этап 1 и 2: Исследование Google Gruyere и перехват HTTP-трафика

### 4.1. Особенности протокола Google Gruyere
Веб-приложение Google Gruyere функционирует по открытому незашифрованному протоколу **HTTP** (по умолчанию на порту `8008`), что позволяет полностью инспектировать передаваемые заголовки, параметры и тело ответов без необходимости перехвата SSL/TLS сертификатов.

### 4.2. Сборка TCP-потоков и декомпрессия gzip
Так как в протоколе TCP передача данных фрагментируется на сегменты, заголовки HTTP-ответа (`HTTP/1.0 200 OK`) и HTML-тело документа часто приходят в разных сетевых пакетах. 

В разработанном скрипте [`script_xss.py`](script_xss.py) реализован алгоритм сборки потока:
1. Пакеты группируются по уникальному 4-кортежу сетевого соединения: `(Client_IP, Client_Port, Server_IP, Server_Port)`.
2. Последовательно склеиваются сегменты от клиента к серверу (HTTP Request) и от сервера к клиенту (HTTP Response).
3. Производится разделение заголовков и тела по стандартному разделителю `\r\n\r\n`.
4. При наличии заголовка `Content-Encoding: gzip` тело автоматически распаковывается через `gzip.decompress()`.

## 5. Этап 3: Рекон-анализ и поиск точек внедрения XSS

В ходе исследования архитектуры Google Gruyere и шаблонизатора **Gruyere Template Language (GTL)** были выявлены следующие особенности:

1. **Обработчик несуществующих URL (`_DoBadUrl`)**:
   При переходе по адресу вида `http://localhost:8008/<unique_id>/<user_input>` вызывается метод `self._SendError('Invalid request: %s' % (path,), ...)`.
2. **Шаблон вывода ошибок (`resources/error.gtl`)**:
   В шаблоне текст ошибки выводится следующим образом:
   ```html
   [[if:_message]]
   <div class='message'>{{_message}}</div>
   [[/if:_message]]
   ```
   В отличие от безопасной конструкции `{{_message:text}}`, конструкция `{{_message}}` в GTL **не экранирует** символы `<`, `>`, `"`, `'` и выводит их в DOM-дерево браузера в исходном (сыром) виде.

### Подготовленные XSS-нагрузки:
* **Вектор 1 (Классический Script Injection)**:  
  `GET /<unique_id>/<script>alert('XSS-Reflected-HSE')</script>`  
  Цель: внедрение исполняемого тега `<script>` непосредственно в тело документа.
* **Вектор 2 (Внедрение через HTML-атрибут тега <img>)**:  
  `GET /<unique_id>/<img src='invalid-image.jpg' onerror='alert("XSS-Img-HSE")'>`  
  Цель: обход возможных фильтров тега `<script>` через обработчик событий `onerror`.

## 6. Этап 4: Анализ перехваченного сетевого трафика (.pcap)

В файле дампа [`captured_traffic.pcap`](captured_traffic.pcap) зафиксированы 4 полные транзакции (92 пакета):

### 6.1. Легитимный трафик (Транзакции #1 и #2)
* **Транзакция #1**: Запрос главной страницы `GET /<id>/ HTTP/1.1`.  
  Сервер возвращает статус `200 OK`, тело ответа составляет **3480 байт** (полная разметка меню и профиля).
* **Транзакция #2**: Просмотр сниппетов `GET /<id>/snippets.gtl HTTP/1.1`.  
  Сервер возвращает статус `200 OK`, размер тела — **2593 байта**.

### 6.2. Атакующий трафик с XSS (Транзакции #3 и #4)

#### Транзакция #3: Reflected XSS через `<script>`
* **HTTP-запрос (пакет ~60)**:
  ```http
  GET /502719744890570617318760618100146259745/%3Cscript%3Ealert%28%27XSS-Reflected-HSE%27%29%3C/script%3E HTTP/1.1
  Host: localhost:8008
  User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Scapy-HW8-Client
  ```
  *Полезная нагрузка передается в пути URL (GET-запрос) в URL-кодированном формате.*
* **HTTP-ответ сервера (пакеты ~62-64)**:
  ```http
  HTTP/1.0 200 OK
  Server: BaseHTTP Python/3.15.2
  Content-type: text/html
  X-XSS-Protection: 0
  
  <!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01 Transitional//EN">
  <html>
  ...
  <div class='message'>Invalid request: /<script>alert('XSS-Reflected-HSE')</script></div>
  </body></html>
  ```
  *Сервер декодировал URL-параметры обратно в сырые байты и без санитизации вставил их в разметку `<div class='message'>`. Браузер исполняет скрипт `alert()`.*

#### Транзакция #4: Reflected XSS через `<img onerror>`
* **HTTP-запрос (пакет ~83)**:
  ```http
  GET /<id>/%3Cimg%20src%3D%27invalid-image.jpg%27%20onerror%3D%27alert%28%22XSS-Img-HSE%22%29%27%3E HTTP/1.1
  ```
* **HTTP-ответ сервера**:
  ```html
  <div class='message'>Invalid request: /<img src='invalid-image.jpg' onerror='alert("XSS-Img-HSE")'></div>
  ```
  *Нагрузка отражена как атрибут DOM-элемента. Браузер пытается загрузить несуществующую картинку и немедленно вызывает обработчик `onerror`.*

## 7. Сравнительный анализ характеристик трафика

| Параметр сравнения | Легитимный трафик (Normal) | Трафик во время XSS-атаки |
| :--- | :--- | :--- |
| **Метод передачи** | `GET /` и `GET /snippets.gtl` | `GET /<id>/<payload>` (через ошибочный путь URL) |
| **Код статуса ответа** | `200 OK` | `200 OK` (ошибка отображается со статусом 200 вместо 404) |
| **Средний размер ответа** | **3036.5 байт** | **2282.0 байт** (страница ошибки компактнее) |
| **Структура HTML-ответа** | Содержит разметку меню, таблицы сниппетов и стили | Содержит шаблон `/error.gtl` с блоком `<div class='message'>` |
| **Экранирование символов** | В штатных шаблонах спецсимволы экранируются | **Отсутствует**: символы `<`, `>`, `'`, `"` передаются открыто |
| **Заголовок безопасности** | `X-XSS-Protection: 0` | `X-XSS-Protection: 0` (сервер отключает встроенную защиту браузера) |

### Выводы по анализу трафика:
1. **Аномалии размера и структуры**: Ответы при XSS имеют характерный меньший размер (~2.2 КБ) и содержат блок `<div class='message'>`.
2. **Отсутствие экранирования (Lack of Output Encoding)**: Главной причиной уязвимости является отсутствие вызова функции HTML-экранирования (`html.escape`) перед конкатенацией данных пользователя в шаблон.
3. **Отключение защиты на уровне заголовков**: Google Gruyere явно передает заголовок `X-XSS-Protection: 0`, предотвращая блокировку скрипта устаревшими браузерными XSS-аудиторами.

## 8. Инструкция по запуску и воспроизведению

Скрипт поддерживает несколько режимов работы через аргумент `--mode`:

### 8.1. Запуск полного цикла
Автоматически проверяет/запускает сервер Gruyere, включает сниффер Scapy, генерирует легитимный и атакующий трафик, сохраняет дамп в `captured_traffic.pcap` и запускает детальный парсер:
```bash
py script_xss.py --mode all
```

### 8.2. Анализ уже сохраненного .pcap файла
```bash
py script_xss.py --mode analyze --pcap captured_traffic.pcap
```

### 8.3. Запуск только сниффера
```bash
py script_xss.py --mode sniff --duration 15 --pcap captured_traffic.pcap
```

### 8.4. Запуск только генерации запросов и атак
```bash
py script_xss.py --mode attack
```
